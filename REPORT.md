## 1. Что это такое

**RoltHall** — CRM-система онлайн-бронирования танцевальных залов в Краснодаре.

Клиент выбирает зал, дату и время на сайте, вносит предоплату (50%) через эквайринг, получает подтверждение в мессенджер. Администратор управляет залами, тарифами и бронированиями через встроенную админ-панель.

Система охватывает весь цикл: от первого касания до завершения аренды, включая напоминания, отмену с возвратом и коммуникацию с клиентом.

## 2. Технический стек

| Слой | Решение | Обоснование |
|---|---|---|
| Frontend | Vanilla JS + HTML/CSS | Shared hosting Beget не поддерживает Node.js/SSR; сборщики не нужны для MVP |
| Backend | Laravel 13, PHP 8.3 | Зрелый фреймворк, удобная ORM и Sanctum; PHP есть на любом хостинге |
| БД | MySQL (Beget shared) | Единственная доступная СУБД на тарифе |
| Аутентификация | Laravel Sanctum (staff) + SHA256-токен (клиент) | Sanctum для сессий персонала; для клиентов полноценная аутентификация избыточна |
| Платёжная система | T-Bank (Тинькофф) | Готовый SDK, популярный в РФ, поддерживает webhook |
| Хостинг | Beget shared hosting | Выбор заказчика; наложил ряд ограничений (см. ниже) |
| Мессенджеры | Telegram Bot API + Max Bot API | Telegram — основной канал уведомлений; Max — дополнительный по запросу |
| Планировщик | Laravel Scheduler + Beget cron | Cron запускает `artisan schedule:run` каждую минуту |

## 4. Модель данных

### Ключевые таблицы

**`users`** — единая таблица для всех ролей:
- `role` (developer / owner / admin / client) через пакет spatie/laravel-permission
- `telegram_chat_id`, `telegram_username`, `telegram_avatar_url`
- `max_chat_id`, `max_username`
- `client_password` — последний сгенерированный пароль (синхронизируется с `clients.client_password`)
- `tg_credentials_msg_id` — ID закреплённого сообщения с паролем в Telegram

**`clients`** — расширение клиентов: `is_blacklisted`, `admin_note`, `admin_note_updated_at`

**`halls`** — залы: `name`, `area_m2`, `capacity`, `equipment` (JSON), `cms` (JSON), `is_active`

**`pricing_rules`** — тарифы: `hall_id`, `booking_format`, `day_type`, `guest_tier`, `price_per_hour`

**`bookings`** — брони:
- `status`: draft → hold → pending_payment → paid → confirmed → completed | cancelled
- `format`: hourly / event / allday
- `pkg_label` — отображаемое название пакета
- `hold_expires_at` — TTL холда (10 минут)
- `total_amount`, `prepayment_amount`

**`action_logs`** — аудит всех действий (логин, создание/отмена брони, уведомления)

## 5. Как работает бронирование

### 5.1 Почасовая и событийная бронь (с оплатой)

```
Клиент → calendar.html → выбирает зал + дату + слоты
    ↓
booking.html → заполняет форму (имя, телефон, email, Telegram/Max)
    ↓
POST /api/bookings/hold
    → BookingService::createHold() — создаёт запись со статусом hold
    → TBankService::init() — получает payment_url от T-Bank
    ↓
Клиент → редиректится на страницу T-Bank → вносит предоплату
    ↓
T-Bank → POST /api/payment/webhook
    → PaymentController — меняет статус на paid/confirmed
    → NotificationService::notifyAdminNewBooking() — уведомление в TG + Max
    → NotificationService::notifyClientConfirmedDual() — клиенту в TG и/или Max
```

### 5.2 Заявка «Весь день» (без оплаты)

```
Клиент → booking.html (формат allday) → выбирает даты
    ↓
POST /api/bookings/inquiry
    → BookingService::resolveClient() — создаёт/находит клиента, сохраняет max_chat_id
    → Создаёт черновые брони (status: draft) для каждой даты
    → NotificationService::sendRaw() — уведомление администратору
    → NotificationService::notifyClientInquiryDual() — «Заявка принята» клиенту
```

### 5.3 Отмена

Клиент или администратор → `POST /api/bookings/{id}/cancel`
- Если до начала брони > 6 часов — оформляется возврат предоплаты
- Клиент получает уведомление в TG и/или Max с информацией о возврате

### 5.4 Напоминания

Команда `SendBookingReminders` запускается планировщиком:
- **За 3 часа до начала** — для почасовых и событийных броней
- **В 20:00 накануне** — для аренды на весь день
- Рассылается в TG и Max одновременно (dual-channel)

## 6. Интеграция Telegram

### Способ получения сообщений от бота

**Проблема:** Beget shared hosting блокирует входящие webhook-запросы от внешних сервисов.

**Решение:** Long-polling через artisan-команду `telegram:poll`:
```
artisan telegram:poll → getUpdates (offset+1, limit 100, timeout 0)
    → TelegramController::processUpdate($update) — та же логика что и webhook
    → Запись последнего offset в storage/app/tg_poll_offset.txt
```
Cron на Beget запускает `schedule:run` каждую минуту, что обеспечивает задержку ответа до 1 минуты — приемлемо для уведомительного бота.

### Команды бота

| Команда | Действие |
|---|---|
| `/start` | Приветствие, кнопки «Забронировать зал» и «Личный кабинет» |
| `/lk` | Отправляет ссылку-кнопку на ЛК (Telegram WebApp) |

### TG WebApp

Личный кабинет (`profile.html`) открывается как Telegram WebApp. При открытии:
1. Получает `initData` из `window.Telegram.WebApp.initData`
2. Отправляет на `POST /api/profile/tg-login` — верифицируется HMAC подпись
3. Получает список броней без пароля

### Учётные данные через Telegram

`sendCredentials(User $user)`:
- Генерирует случайный пароль (8–12 символов, гарантированно со спецсимволами)
- Отправляет сообщение с паролем в Telegram, закрепляет его (`pinChatMessage`)
- Удаляет предыдущее закреплённое сообщение
- Обновляет `client_password` в БД

## 7. Интеграция Max Messenger

### Архитектура

**Max Bot API** (`platform-api.max.ru`) — российский мессенджер с Bot API аналогичным Telegram. Ключевые отличия:
- Webhook поддерживается и работает (в отличие от Beget + Telegram)
- Для отправки сообщений: `POST /messages?user_id={id}` или `?chat_id={id}`
- `Authorization: {token}` (без `Bot` префикса, в отличие от Telegram)
- Кнопки: тип `inline_keyboard` с вложенным массивом `payload.buttons`

### Команды бота

| Команда | Действие |
|---|---|
| `/start` | Приветствие + ID пользователя + кнопки + подсказка написать `/lk` |
| `/lk` | Если аккаунт привязан → отправляет свежий пароль; иначе → предлагает забронировать |
| `/booking` | Кнопка «Открыть календарь» со встроенным max_id в URL |

### Привязка аккаунта

`max_chat_id` сохраняется автоматически при первом контакте с ботом (`handleMessage`) или при оформлении брони (`resolveClient()` из `BookingController::inquiry()`).

Форма бронирования при переходе `?via=max&max_id=XXX`:
- Поле Telegram трансформируется в поле Max (иконка, label, readonly, значение = max_id)
- Поля имя/телефон/email предзаполняются из `GET /api/auth/max-profile?max_id=`
- Параметры `via=max&max_id` сохраняются при переходе calendar → booking
- API-запрос отправляет `max_user_id`, не `telegram` (разные поля в БД)

### Учётные данные через Max

`sendCredentialsMax(User $user)`:
- Генерирует новый пароль (тот же алгоритм что для TG)
- Отправляет в Max сообщение с телефоном и паролем + кнопка «Войти в ЛК»
- Обновляет `client_password` в БД
- В отличие от TG: нет закрепления сообщений (Max API не поддерживает)

### Шаблоны уведомлений

В настройках Max (admin-панель → вкладка Max) можно задать кастомные шаблоны с переменными `{name}`, `{hall}`, `{date}`, `{time}`, `{amount}` и т.д. Если шаблон не задан — отправляется дефолтный текст.

## 8. Dual-channel уведомления

Все клиентские уведомления поддерживают одновременную отправку в TG и Max:

| Событие | TG | Max | Кнопка ЛК в Max |
|---|---|---|---|
| Бронь подтверждена | ✅ | ✅ | ✅ |
| Бронь отменена | ✅ | ✅ | ✅ |
| Напоминание (3ч / накануне) | ✅ | ✅ | ✅ |
| Заявка принята (весь день) | ✅ | ✅ | ✅ |
| Учётные данные (пароль) | ✅ | ✅ | ✅ |
| Новая бронь (администратору) | ✅ | ✅ | — |

Принцип: уведомление идёт во все каналы где `chat_id != null`. Отправка в один канал не блокирует другой — ошибки логируются в `action_logs`.

## 9. Роли и права доступа

| Роль | Что может |
|---|---|
| **developer** | Всё, включая debug-лог, удаление данных, настройки ботов |
| **owner** | Всё кроме debug-лога; редактирование контактов клиентов |
| **admin / manager** | Просмотр броней и клиентов, создание броней, заметки |
| **client** | Просмотр своих броней через ЛК (профиль), отмена |

Аутентификация:
- **Персонал:** Sanctum-токен (email + password), хранится в `localStorage`
- **Клиент:** SHA256-токен без пароля (из phone + email + app.key), хранится в `sessionStorage`
- **Telegram WebApp:** HMAC-верификация через initData (без токена)

## 11. Важные архитектурные решения

### Shared hosting вместо VPS
**Ограничение:** нет возможности держать постоянный процесс, нет Redis, нет очередей, Telegram webhook заблокирован.
**Следствия:**
- Polling вместо webhook для Telegram
- File-based cache для polling offset (не Redis)
- Все задачи через Laravel Scheduler → cron (работает)
- Max webhook работает нормально — platform-api.max.ru не заблокирован

### Отказ от magic link для Max
Изначально планировался автологин через одноразовую ссылку (JWT/HMAC токен в URL). Три подхода последовательно не сработали:
1. `Cache::put()` — разные PHP-процессы на Beget не шарят кэш
2. HMAC-подписанный URL — ошибка верификации (причина не установлена)
3. URL-safe base64 — то же поведение

**Решение:** отправлять телефон + сгенерированный пароль прямо в сообщении. Плюсы — работает надёжно; минус — пароль виден в чате (приемлемо для данного контекста, т.к. отправляется в личку).

### Unified-login вместо классического
Один эндпоинт `POST /api/auth/unified-login` принимает телефон + email, определяет роль и выдаёт нужный тип токена. Это позволяет одному и тому же экрану входа обслуживать и персонал (→ `/admin`) и клиентов (→ `/profile`).

### SHA256-токен для клиентов
Клиентский профиль не требует настоящей сессии — нужно только убедиться что пользователь тот за кого себя выдаёт. SHA256 от неизменяемых данных (id + phone + email + app.key) работает как детерминированный «пароль» без хранения сессии.

### CMS залов через publishHall
Контент зала (описание, тарифы, правила) хранится в JSON-поле `cms` и одновременно синхронизируется с реляционными таблицами `pricing_rules`. При публикации из UI происходит двусторонняя синхронизация: данные из UI → `pricing_rules` и обратно `pricing_rules` → CMS JSON. Это позволяет менять цены через CMS-интерфейс без прямого SQL.

## 12. Возможности системы (итог)

### Для клиента
- Выбор зала, даты, времени с проверкой доступности в реальном времени
- Три формата аренды: почасовая, событие (пакет на несколько дней), весь день (заявка)
- Онлайн-оплата предоплаты 50% через T-Bank
- Уведомления о брони в Telegram и/или Max
- Напоминания: за 3 часа до начала или накануне (для аренды на день)
- Самостоятельная отмена с автовозвратом при раннем отказе
- Личный кабинет с историей броней (через сайт или Telegram WebApp)
- Сброс пароля через бота без звонка в офис

### Для администратора
- Управление залами: создание, редактирование, публикация, деактивация
- Тарифная сетка: по дням недели, формату бронирования, количеству гостей
- Список и карточка клиента: история, заметки, blacklist, редактирование контактов
- Создание бронирований вручную
- Аналитика: выручка, загруженность, heatmap, экспорт CSV
- Лог всех действий в системе
- Кастомные шаблоны уведомлений для Max
- Настройки TG и Max ботов из интерфейса
